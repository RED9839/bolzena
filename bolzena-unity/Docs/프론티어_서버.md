## 1. API

모든 응답은 JSON(`cache-control: no-store`, 랭킹만 30초 공개 캐시). 오류는 `{ "error": "…" }` + 상태 코드.
로그인은 **웹 = HttpOnly 쿠키 `bz_s`**, **PC = `Authorization: Bearer <토큰>`**. 바꾸는 요청을 쿠키로 보내면 다른 사이트에서 온 것(Origin 호스트가 다름)은 403.
**정지된 계정**(운영 조치 — §11)은 바꾸는 요청이 모두 403 `{ error: "banned", banned: true, why, until(유닉스 초 · 영구면 null), forever }` — 로그아웃 · 기기 코드 승인(로그인) · 탈퇴만 된다. 읽기(`/api/me` 의 `ban` · 슬롯 목록 · 내 기록)는 그대로. 정지 · 랭킹 숨김 중인 사람은 랭킹 · 남의 편성 보기(404)에서 빠진다.

### 사도 슬롯
**사도마다 10칸까지**(2026-10-19 사용자 「사도마다 저장 칸 10칸까지」 — `LIMIT.SLOTS_PER_HERO`. 10-18 의 「한도 없음」 을 바꿈 · 그 전엔 칸 0~2). 「새로 저장」 할 때마다 서버가 칸 id 를 준다.
11번째 새로 저장은 **409 `{ error: "hero slots full", max: 10, have }`** — 화면은 「덮어쓸 칸을 고르세요」. 덮어쓰기 · 이름 · 지우기는 한도와 상관없다. 이와 따로 남용 막이로 **계정 전체 안전 한도 1,000칸**(`LIMIT.SLOTS_PER_USER` — 아래 §남용 막기).

**이미 10칸을 넘은 사도(한도 전에 저장한 칸):** 지우지 않는다 — 목록에 다 보이고(읽기) · 덮어쓰기 · 이름 · 지우기 · 프론티어 편성은 그대로 되고, **새로 저장만** 그 사도의 칸이 10개 아래로 줄 때까지 409(`have` 에 지금 칸 수). 화면은 칸 수를 「12 / 10」 처럼 붉게 보이고 「새로 저장」 자리에 「10칸이 다 찼습니다 — 덮어쓸 칸을 고르거나 지우세요」. 2026-10-19 공개판에는 사도당 10칸을 넘은 사람이 없어(칸 0~몇 개) 실제로 걸리는 사람은 없다 — 운영 복구 · 옛 주소로 만든 칸이 넘길 때를 위한 규칙. 마이그레이션은 필요 없다(표 모양 그대로 · 한도는 코드).

| 주소 | 하는 일 |
|---|---|
| `GET /api/slots[?hero=]` | `{ slots: [{ id, hero, n, name, status, why, hash, created, updated, slot, best }], count, max: { perHero: 10, perUser: 1000 }, bestSeason }`(한도를 넘은 칸도 다 준다). `n` = 그 사도의 저장 차례(0부터), `name` = 칸 이름(없으면 null — 화면은 「〇〇 저장 n+1」). `best` = **지금 시즌에 이 칸(지금 글)으로 낸 검증된 최고** `{ score, at, attempt }` 또는 null — 시도가 시작 때 적어 둔 슬롯 지문(`attempts.slot_hashes` = `hero_slots.hash`)과 견준다. 덮어쓰면 지문이 바뀌어 새로 센다 |

| `DELETE /api/slot/:id` | 칸 지우기 → 204(이미 시작한 시도는 떠 둔 슬롯으로 그대로 검증) · 남의 칸 · 없는 칸 404 |
| `PUT /api/slots/:hero/:n` · `DELETE /api/slots/:hero/:n` | **옛 주소(0005 전 게임과의 호환)** — 차례 n(0 이상 아무 번호) 칸에 올림(없으면 만듦 — 이때만 한도: 사도 10칸 · 계정 1,000칸, 같은 409) · 덮어씀(이름 그대로) · 지우기. 응답에 `id` 가 더해졌다 |

status: `pending`(검증기가 아직) · `ok`(HeroSlot.Check 통과) · `bad`(why 에 까닭). 덮어쓰면 다시 pending.

**칸 이름**(선택 — 카제나 「세이브 데이터」 이름 편집처럼): NFKC · 앞뒤 공백 정리(사이 공백은 하나로) · **16자** · 닉네임과 같은 글자(한글 · 영문 · 숫자 · 공백 · _ - .) · 글자나 숫자 하나는 있어야. 이름은 주인만 본다(남의 편성 보기 · 랭킹에는 나가지 않는다) — 그래서 사칭 금지어는 보지 않는다.

| `GET /api/frontier/attempt/:id` | **시도 하나의 편성** — 시작 때 떠 둔 슬롯 셋(카드 · 장비 · 성장) · 점수 · 끝 · 닉네임 → `{ attempt, mine, name, season, heroes, at, status, score, over, played, slots: [{ hero, slot }] }`. **내 것**(로그인한 주인)이면 상태와 관계없이 + `claimed · why · turn · sent`. **남의 것은 랭킹에 오르는 것만** — verified 시도는 편성까지, **검증 전(pending) 시도는 줄만**(`slots: null` · `score` = 주장 점수 · `status: "pending"` — 화면은 「편성은 검증된 뒤 공개」 알림), 거절 · 안 냄 · 진행 중은 404 · 슬롯의 `from.seed`(뜬 판 씨앗)도 뺀다. 언제나 빼는 것: 서버 씨앗 · 테이프 · 사용자 내부 번호 · 슬롯 번호. 로그인 없이(남의 것) · IP 분당 120 |

**테이프를 글로 받는 까닭:** 엔진 셋업에 `1.0` 같은 실수가 있고, 검증기는 「슬롯으로 다시 지은 셋업」 과 테이프 셋업을 JSON 토큰으로 견준다. JS 가 `JSON.parse → stringify` 하면 `1.0` 이 `1` 이 되어 진짜 테이프도 「셋업이 다르다」 로 거절된다(로컬 시험에서 실제로 봤다). 그래서 서버는 글을 손대지 않고 둔다 — 게임도 `FrontierTape.Json()` 을 그대로 보내야 한다.

### 검증 대상 — 자기 최고 기록 후보만(2026-10-19 사용자 · `Web/lib/score.js`)
| 언제 | 하는 일 |
|---|---|
| 낼 때(`submit`) | 그 사람 · 그 시즌의 **지금 최고**(verified · pending 가운데 가장 높은 점수 — 검증 전은 주장 점수)보다 **높으면 pending**(검증 대기열 · 랭킹 「검증 전」), **같거나 낮으면 skipped**(「검증 안 함」 — 검증기가 가져가지 않고 랭킹에도 들지 않는다. 그 사람의 더 높은 줄이 이미 있으니 랭킹은 같다) |
| 최고 후보가 빠질 때 | 검증기 rejected(`/api/verify/result`) · 운영 `score.reject` · `score.delete` 뒤 — 남은 최고(verified · pending)보다 높은 skipped 가운데 **가장 높은 것 하나**(같으면 먼저 낸 것)를 pending 으로 올린다(`promoteNext`). 그것도 거절되면 다시 다음 것. 결과 응답에 `promoted`(올린 점수 id) |
| 검증기 | `/api/verify/pending` 은 pending 만 준다 — skipped 는 안 본다. 같은 실행에서 올라온 후보는 대개 다음 실행(5분 뒤)에 본다 |
- 테이프는 skipped 도 그대로 둔다(나중에 올라오면 그 테이프로 검증).
- 내 기록 · 그때의 편성: skipped = 「검증 안 함」(회색) · 까닭 한 줄 「낼 때 내 최고보다 높지 않아 검증하지 않음」. 남에게는 404(랭킹에 없으니).
- **칸별 최고**(`GET /api/slots` 의 `best` — `{ score, at, attempt, status, verified }`): **검증된 것 우선** — 그 칸(지문)으로 낸 검증된 점수가 하나라도 있으면 그 가운데 최고(더 높은 검증 전 · 검증 안 함 점수가 있어도). 검증된 것이 없으면 pending · skipped 가운데 가장 높은 주장 점수 + status — 화면 「이 칸 최고 · 검증됨 / 검증 전 / 검증 안 함」. rejected 는 세지 않는다.
- 시험(run-local 「승격」): P 가 lo(첫 점수 → pending) · 위조 149,999(→ pending) · mid · hi(→ skipped) → 대기열은 lo · 위조 둘만 → 검증: lo verified · 위조 rejected → **hi 승격**(mid 는 그대로 skipped) · 랭킹 P 줄 = hi 「검증 전」 · 칸별 최고 = lo(검증된 것 우선) → 다시 검증: hi verified → 운영 `score.reject` hi → **mid 승격**(`promoted`).

### 랭킹 규칙 — 검증 전 점수도 바로(2026-10-19 사용자 「중간 방법 1」)
검증기(이 PC — §4)가 몇 분마다 돌아서, 낸 뒤 랭킹에 오를 때까지 기다리지 않게 했다.
| 상태 | 랭킹(`/ranking`) · 내 최고(`/me` best · rank) | 남의 편성 보기(`/attempt/:id`) | 내 기록(`/history` · `/me` scores) |
|---|---|---|---|
| pending(검증 전) | **오른다** — 점수 = 주장 점수(제출 상한을 지난 것) · `verified: false` → 화면 회색 작은 「검증 전」 | **줄만**(`slots: null`) — 편성은 검증된 것만 공개 | 「검증 전」 |
| verified | 오른다 — 점수 = 검증기가 다시 돌린 점수(= 주장 점수) · 표시 없음 | 편성까지 | 「검증됨」 |
| rejected | **빠진다** — 그 사람의 다음 줄(검증됐거나 검증 전인 것)이 대신 오른다 · skipped 가운데 더 높은 것이 있으면 pending 으로 올라 「검증 전」 으로 | 404 | 「거절됨」 + 까닭 |
| skipped(검증 안 함) | 안 든다(그 사람의 더 높은 줄이 이미 있다) | 404 | 「검증 안 함」(회색) |
- 사람마다 **가장 높은 줄 하나**(검증 여부와 관계없이) — 검증 전 점수가 그 사람 최고면 그 줄이 오른다. 같은 사람의 같은 점수면 검증된 줄을 고른다. 순서는 점수 높은 차례 · 같으면 먼저 낸 쪽.
- 정지 · 숨김(`VISIBLE`) · 닉네임 없음 규칙은 그대로 — 검증 전 줄도 같이 빠진다.
- 칸별 최고는 위 「검증 대상」 의 규칙(검증된 것 우선).
- 위험: 위조 점수도 검증기가 돌 때까지(PC 가 켜져 있으면 5분 안) 「검증 전」 으로 보인다 — 그래서 받는 순간 말이 안 되는 점수는 아래 「제출 상한」 으로 막는다. 버전이 다른 테이프(검증기가 건너뜀)는 검증기를 맞출 때까지 「검증 전」 으로 남는다.

### 제출 상한(0008 — 2026-10-19 사용자 「중간 방법 2」)
`submit` 이 모양 검사 뒤 바로 400 `over cap: …`(`why` 같은 글)으로 거절한다 — 점수 줄을 만들지 않고 시도도 「낸 것」 이 되지 않는다.
| 검사 | 값 · 근거 |
|---|---|
| 점수 모양 | 정수 0~10⁹ — 음수 · 소수 · 글은 400 `bad score`(전부터) · 주장 점수 = 테이프 점수(전부터) |
| 점수 ≤ `seasons.score_max` | 프리시즌 **150,000** = M.E.O.W 최대 HP(`bolzena-content-v2/world/프론티어/프리시즌.json` hp 150000 × 시즌 hp 1). 점수는 보스가 잃은 HP 합(넘친 피해 빼고)이라 회복하지 않는 보스면 넘을 수 없다 — **2026-10-24 개정 뒤 점수 = 피해 + 방어**(막은 보스 피해 ×10 — 프론티어_설계.md 「M.E.O.W 10-24 개정」)라 보스를 쓰러뜨리면 600,000 을 넘는다(측정 최고 661,070) → 700,000(보스_개정_1024_실행서.md) |
| 1 ≤ 낸 턴 ≤ 시즌 턴(10) · 「time」 이면 낸 턴 = 시즌 턴 | 엔진 `Frontier.Tape` — `Played = min(Turn, Turns)` |
| 턴 지문 수 ∈ {낸 턴, 낸 턴 + 1} · ≤ 시즌 턴 + 1 | 지문은 연 직후 하나 + 턴을 넘길 때마다 하나(봇 테이프: time 10턴 → 11개 · lose k턴 → k+1 개) |
| 점수 ≤ 낸 턴 × `seasons.turn_max` | 프리시즌 **90,000**. 테이프에는 턴별 피해가 없다(턴 지문은 해시) — 그래서 「턴당 평균의 상한」 으로 본다. 근거: `bz frontier 400 --fights 1500 --slotbot both --fightbot both`(다듬은 슬롯 · 3,000판) + `bz frontier 200 --fights 400`(800판) 에서 **한 턴 최대 피해 29,972**(상위 1% 17,132 · 가운데 4,641 — `FrontierSim` 이 턴마다 보스 `Lost` 증가를 잼) → 약 3배. 사람이 봇보다 잘 몰아쳐도 닿기 어려운 선, 1~2턴에 보스를 거의 다 깎는 위조를 막는다 |
| 크기 | 테이프 256KB(봇 평균 17.7KB) · 수 5,000 · 턴 지문 200(전부터) |
- 값이 NULL 이면 그 검사는 건너뛴다 — 새 시즌을 넣을 때 `score_max`(보스 최대 HP × 시즌 hp) · `turn_max`(그 보스로 `bz frontier` 를 돌려 「한 턴 최대 피해」 의 약 3배)를 채운다. 회복하는 보스면 `score_max` 를 비우거나 넉넉히.
- 상한을 바꿀 때(원격): `UPDATE seasons SET turn_max = … WHERE id = '…'` — 운영자가 D1 에 직접(배포 필요 없음).

### 시험 계정(0009 — 2026-10-20 사용자 「사도 카드 원하는 덱 만들어서 프론티어 테스트」)
운영자가 정한 계정(`users.role = 'tester'`)만 「덱 만들기」 로 만든 덱을 서버에 올려 프론티어를 시험한다. 운영자 계정 RED9839 에 줄 것(§7 「0009」).
- **역할은 서버만 판단한다** — `lib/auth.js` `current` 가 `users.role` 을 읽고, 시험 칸 주소 · `start` 가 그것만 본다(게임이 보내는 값 · 머리는 믿지 않는다 — run-local 시험 「x-role」). 게임은 `/api/me` 의 `user.role` 로 진입점만 보인다.
- **부여 · 회수는 운영 조치로만** — `POST /api/admin/act { action: "role", user, role: "tester" | null, reason }` · `bz admin role <대상> tester|none --reason 까닭 [--yes]`(§11). 운영 기록에 `{ from, to }`. 같은 값이면 409 · 모르는 역할 400.

| 주소 | 하는 일 |
|---|---|
| `GET /api/test/slots[?hero=]` | 내 시험 칸 `{ slots: [{ id, hero, name, hash, created, updated, test: true, slot }], count, max: 100 }` |
| `POST /api/test/slots?hero=키[&name=이름]`(본문 = HeroSlot JSON 글) | 새 시험 칸 → 201. **일반 칸과 따로**(`test_slots` 표 — 사도당 10칸 한도와 별개 · 계정당 100칸 `LIMIT.TEST_SLOTS_PER_USER` · 넘으면 409 `test slots full`) · **규칙 검사 생략**(상태가 없다 — 검증기가 보지 않는다) · **크기 · 형식 검사는 그대로**(16KB · `lib/slot.js shape` — 모르는 키 · 완주 표시 · 카드 40장 · 주소 사도 = 슬롯 사도) |
| `PUT` · `PATCH { name }` · `DELETE /api/test/slot/:id` | 덮어쓰기(같은 사도만) · 이름 · 지우기(204). 남의 칸 · 없는 칸 404 |
| `POST /api/frontier/start { slots: [{ test: id }, …] }` | 시험 칸으로 도전(일반 칸 `{ id }` 와 섞어도 된다) → 응답 `test: true` · `slots[i].test = id`. 시험 칸은 규칙 밖이어도 시작된다 |

- **일반 계정이 시험 칸 주소(목록 · 저장 · 덮어쓰기 · 지우기)를 부르거나 `start` 에 `{ test }` 를 넣으면 403 `{ error: "tester only" }`**(로그인 전 401 · 가입 전 403 `needsName` · 정지 403 `banned` — 쓰기 규칙은 일반 칸과 같다).
- **시험 계정이 연 시도는 모두 시험**(`attempts.test = 1` — 시험 칸이든 일반 칸이든) → 낸 점수는 `scores.test = 1` · **status `skipped`(검증 안 함)**:
  - 랭킹 · 남의 편성 보기(404) · 내 순위(`/me` rank null) · 내 최고(`/me` best) · 칸별 최고 · 다음 후보 올리기(`promoteNext`)에서 빠진다 — 쿼리마다 `s.test = 0`, 그리고 `VISIBLE` 이 `u.role IS NULL` 도 본다(숨김과 같은 자리 — 역할을 받기 전에 낸 점수도 시험 계정인 동안은 빠진다).
  - 줄에 적힌 표시라 **역할을 회수해도 시험 점수는 계속 빠진다**(회수 뒤 새 도전은 보통 시도).
  - 본인 기록(`/history` · `/me` scores · `/attempt/:id`)에는 `test: true` — 화면 칩 「시험」 · 「시험 기록 — 랭킹 · 남의 편성 · 내 순위에 오르지 않음」.
- **검증기 결정: 시험 점수는 검증하지 않는다(건너뜀).** 늘 skipped 로 들어가 `/api/verify/pending` 이 가져가지 않고(그 질의도 `s.test = 0` — 운영 조치로 상태가 바뀌어도 안 준다), 시험 칸은 규칙 밖일 수 있어 검증기(`Frontier.Verify` + 슬롯)는 「슬롯으로 열 수 없다」 로 거절할 것이라 돌려 볼 뜻이 없다. 테이프는 다른 점수처럼 남는다(필요하면 `bz frontier --verify` 로 손으로).
- 회수하면 시험 칸은 남는다(다시 주면 그대로) · 탈퇴하면 같이 지운다. 운영 사용자 보기에 `role` · `testSlots` · `scores.test` · 최근 시도 `test`.

### 1.5 가입 · 닉네임(회원가입식 — 2026-10-18 사용자)
- **첫 로그인**(디스코드 · 구글 · PC 기기 코드)에 사용자 줄만 만들고 닉네임은 비워 둔다. 디스코드 · 구글 이름은 가져오지 않는다(받는 범위는 그대로 identify · openid).
- `/api/me` 가 `needsName: true` 를 주는 동안은 **가입 전** — 슬롯 올리기 · 프론티어 시작 · 제출이 403 `{ error: "name required", needsName: true }`. 랭킹 · 시즌 읽기 · 슬롯 목록 · 로그아웃 · 탈퇴는 된다.
- **닉네임을 정하면 가입 끝**(`POST /api/me/name`). 규칙(`Web/lib/nick.js`):
  | 규칙 | 값 |
  |---|---|
  | 정리 | NFKC(전각 → 반각 — 「Ａｌｉｃｅ」 → 「Alice」 · 조합형(NFD) 한글 → 완성형 · ⓐ → a) · 앞뒤 공백 빼고 사이 공백은 하나로(전각 공백 · 줄 바꿈 없는 공백 · BOM 도 공백으로). **한글 호환 자모(ㄱ-ㅎ ㅏ-ㅣ)는 NFKC 에 넣지 않는다** — NFKC 가 「ㅋㅋ」 를 첫가끝 자모로 바꿔 쓸 수 없는 글자로 만들던 것(2026-10-19 시험에서 찾아 고침) |
  | 길이 | 2~12자(정리한 뒤, 글자 단위) |
  | 글자 | 한글(완성형 · 자모) · 영문 · 숫자 · 공백 · `_` `-` `.` 만 — 제어 문자 · HTML(`<>`·따옴표) · 보이지 않는 글자(폭 없는 공백 따위) · 이모지는 못 씀. 글자나 숫자가 하나는 있어야 함 |
  | 겹침 | 열쇠 = 정리한 이름의 소문자에서 공백 · `_` `-` `.` 를 뺀 것. 다른 사람 열쇠와 같으면 409(「ALICE」 = 「Alice」 = 「ａｌｉｃｅ」, 「앨리스01」 = 「앨리스 01」). D1 유일 색인 `users_nick_key`(0003) 가 동시 요청도 막는다(다섯이 동시에 같은 이름 → 200 하나 · 409 넷 — 시험). 가입 · 바꾸기 · 운영 rename 이 같은 열쇠 · 같은 색인을 쓴다 |
  | 비슷한 글자(정책) | 키릴 · 그리스 글자(Аlice · Αlice)는 쓸 수 있는 글자가 아니라 400. **라틴 o / 숫자 0 · l / I / 1 은 다른 이름으로 본다**(「A1ice」 ≠ 「Alice」) — 접으면 「Bob1」 · 「Bobl」 처럼 멀쩡한 이름끼리 막히고, 영문 닉네임 고르기가 크게 좁아진다. 사칭이 문제되면 운영 rename 으로 다룬다. 금지어 검사만 접어 보는 것(「b0lzena」 · 「adm1n」 막기)은 사용자 판단 대기 |
  | 이름이 풀리는 때 | 탈퇴하면 사용자 줄이 지워져 그 이름은 **바로** 남이 쓸 수 있다 · 운영자가 비우면(clearname) 바로 풀린다 · 본인은 비워진 뒤 처음 정하기처럼 바로 다시 정한다(남이 먼저 가져가면 409) |
  | 금지어(운영자 · 공식 사칭) | 열쇠에 들어 있으면 안 됨: 운영자 · 운영진 · 운영팀 · 관리자 · 개발자 · 볼제나 · bolzena · admin · moderator · official · 공식 · 에피드 · epidgames / 열쇠가 딱 이것이면 안 됨: gm · mod · staff · system · 시스템 · 운영 · 관리 → 400 |
  | 바꾸기 | 같은 주소로. 처음 정하기는 언제든, 그 뒤 바꾸기는 **24시간에 한 번**(429 `retryAfter` 초). 지금 이름과 같으면 그대로 200(횟수 안 씀) |
- 랭킹에 보이는 이름 = 닉네임. 닉네임을 바꾸면 지난 점수의 랭킹 줄도 새 이름으로 보인다.

**화면(유니티 — 다음 단계)이 할 일:** 로그인 뒤 · 게임 시작 때 `/api/me` 를 보고 `needsName` 이면 **닉네임 창**을 띄운다(규칙 한 줄 안내, 400 이면 `why` 를 그대로 보여 주고, 409 면 「이미 누가 쓰는 닉네임」). 정하기 전에는 사도 저장 · 프론티어 단추를 막거나 누르면 이 창을 띄운다(403 `needsName` 을 받아도 같은 창). 설정에 「닉네임 바꾸기」(하루 한 번 — 429 면 남은 시간 표시). PC 빌드도 기기 코드 로그인 뒤 같은 창.

| `POST /api/verify/result { slots: [{ id, hash, status, why }], scores: [{ id, status, score \| why, turn }] }` | 슬롯은 hash 가 지금 것과 같을 때만(검증 중에 덮어쓴 슬롯은 대기로 남음), 점수는 pending 일 때만 · verified 는 점수 = 주장 점수일 때만 |

### 운영자 전용(`Authorization: Bearer <ADMIN_TOKEN>` — 검증기 토큰과 따로)
`GET /api/admin/user` · `GET /api/admin/log` · `POST /api/admin/act` — 자세히 §11. `ADMIN_TOKEN` 이 없거나 32자보다 짧거나 `VERIFY_TOKEN` 과 같으면 셋 다 503.

**사도 10칸인 까닭(2026-10-19 사용자):** 저장 칸은 보스전용 덱을 몇 벌 골라 두는 자리 — 화면이 「있는 칸 + 새로 저장 n/10」 한 목록으로 정리되고, 그 사도의 칸 목록 · 저장 창이 끝없이 길어지지 않는다. **1,000칸인 까닭:** 사도 20명 × 10칸 = 200칸이라 일반 플레이로는 닿지 않는다(옛 칸 · 운영 복구가 사도 한도를 넘겨도 계정 쪽은 버틴다). 막는 것은 스크립트로 칸을 끝없이 만드는 남용뿐. 1,000칸 × 16KB 상한 = 사용자 하나 최대 16MB(실제 슬롯은 1~2KB 라 1~2MB)로 D1 · 목록 응답(`GET /api/slots` 는 한 번에 다 준다)이 감당한다. 닿으면 409 → 화면은 「안 쓰는 칸을 지워 주세요」.

쓰는 요청의 속도 제한은 D1 `rate` 표(열쇠 「무엇|사용자」 또는 「무엇|IP 해시 앞 16자리」 · 창이 지나면 지움).

## 3. 로그인 흐름

### 웹(WebGL — 같은 도메인)
1. 게임의 로그인 단추 → 같은 탭에서 `/api/auth/discord/start?back=/`(판 저장이 먼저 되어 있어야 함 — 게임이 다시 로드된다).
2. 서버가 state(구글은 + PKCE)를 짧은 쿠키에 두고 디스코드(`scope=identify`) · 구글(`scope=openid`)로 보냄.
3. 공급자 → `/api/auth/<공급자>/callback?code&state` → state 맞춤 → 코드를 토큰으로(클라이언트 시크릿은 Pages 시크릿) → 디스코드는 `users/@me` 의 `id` 만, 구글은 id_token 의 `sub` 만(iss · aud · exp 확인).
4. 사용자 찾기/만들기(처음이면 닉네임 없는 줄) → 세션 토큰(무작위 32바이트) → 해시만 D1 → 쿠키 `bz_s`(HttpOnly · Secure · SameSite=Lax · 30일) → `back` 으로.
5. 게임은 `/api/me` 로 로그인 여부 · 닉네임을 안다(브라우저가 쿠키를 알아서 붙인다). `needsName` 이면 닉네임 창 → `POST /api/me/name` 으로 가입 끝(§1.5).

### PC 빌드(기기 코드)
1. 게임 `POST /api/auth/device` → `userCode`(예: `K7QM-2M9X`) · `verifyUrl` 을 화면에 띄우고 `Application.OpenURL(verifyUrl)`.
2. 사용자가 브라우저에서 디스코드 · 구글 로그인 → 승인 화면에서 코드가 같은지 보고 「승인」.
3. 게임은 `interval`(5초)마다 `POST /api/auth/device/poll` → 승인되면 `token` 을 받아 기기에 저장, 그 뒤 모든 요청에 `Authorization: Bearer`.
4. 처음 가입이면 `/api/me` 의 `needsName` 을 보고 게임 안 닉네임 창 → `POST /api/me/name`(Bearer).
5. 로그아웃은 `POST /api/auth/logout`(그 토큰만) · 모든 기기는 `?all=1`.

## 6. 사용자가 해야 할 일

### 디스코드 앱 등록
1. https://discord.com/developers/applications → New Application(이름 예: 「볼제나」).
2. OAuth2 → Redirects 에 넣기: `https://bolzena.pages.dev/api/auth/discord/callback`
3. OAuth2 → Client ID 를 적어 두고, Client Secret → Reset Secret 으로 받아 둔다(한 번만 보인다).
4. 범위는 서버가 `identify` 만 요청한다(이메일 · 서버 목록 안 받음). 봇은 만들지 않아도 된다.

### 구글 OAuth 클라이언트
1. https://console.cloud.google.com → 새 프로젝트(예: 「bolzena」).
2. APIs & Services → OAuth consent screen(Google Auth Platform → Branding/Audience): User type **External**, 앱 이름 · 지원 메일 · 개발자 연락처. 범위는 **openid 만**(민감 범위가 없어 심사 없음). 게시 상태를 「In production」 으로(테스트 상태면 등록한 시험 사용자만 로그인됨).
3. Credentials → Create credentials → OAuth client ID → Application type **Web application** →
   - Authorized redirect URIs: `https://bolzena.pages.dev/api/auth/google/callback`
   - (Authorized JavaScript origins 는 필요 없음)
4. Client ID · Client secret 을 받아 둔다.

### 개인정보 안내 글(공개 전에)
게임 · 사이트 어딘가에 아래 「개인정보」 내용을 짧게 띄우고, 탈퇴(`DELETE /api/me`) 단추를 둔다(화면은 4단계 유니티 작업).

## 9. 남은 위험 · 할 일

1. **슬롯 위조(설계 §6.1)** — 규칙 검사로는 「합법한 최강 덱」 을 못 막는다. 그래서 프리시즌 표시(`preseason: true`). 판 전체 검증(7단계) 뒤 정식 시즌.
2. **테이프 글 그대로** — 게임이 테이프를 다시 직렬화하면(`1.0` → `1`) 진짜도 거절된다. 유니티 쪽은 `FrontierTape.Json()` 글을 그대로 `tape` 문자열로 보낼 것. 엔진의 셋업 견주기를 수 값 기준으로 바꾸면 더 튼튼해진다(엔진 손질 — 이번엔 안 함).
3. **검증기 = 이 PC** — PC 가 꺼지면 대기가 쌓인다. 엔진 · 콘텐츠를 배포했는데 검증기를 다시 빌드 안 하면 새 테이프는 「버전 다름」 으로 건너뛴다(로그에 남음). 시즌에 지문을 박으면 어긋날 때 거절된다.
4. **유니티 ↔ .NET 8 교차 확인 전**(설계 §1.2 · 3단계) — WebGL · PC 빌드가 만든 테이프가 `bz` 에서 같은 지문이 나오는지 아직 못 봤다. 어긋나면 진짜 플레이도 rejected. 공개 전에 빌드 테이프로 꼭 시험.
5. **OAuth 실제 왕복은 시험 못 함** — 로컬엔 디스코드 · 구글 앱이 없다. 콜백 처리 코드는 공식 문서 흐름대로 썼지만, 앱 등록 뒤 실제 로그인으로 처음 확인한다(디스코드 `prompt=none`, 구글 `openid` 만 · PKCE).
6. **속도 제한이 D1 쓰기를 쓴다** — 쓰는 요청마다 한 번. 무료 한도(하루 쓰기 10만 줄 — 값 확인 필요) 안이지만 사람이 많아지면 Cloudflare Rate Limiting 규칙으로 옮길 것. 읽기 제한은 서버 조각 메모리라 느슨하다.
7. ~~하루 시도 20번~~ → 2026-10-19 한도 없앰(설계 결정 7). 시도 2시간은 그대로. 재시도가 늘어도 검증기는 그 사람의 최고 후보만 다시 돌린다(§검증 대상) — 검증 부담은 「최고를 갈아 치운 횟수」 만큼.
8. ~~유니티 화면 없음~~ → 4단계(2026-10-18)에 만듦 — 아래 §10.
9. **정지를 탈퇴로 피할 수 있다** — 탈퇴하면 사용자 줄(공급자 번호 HMAC)이 지워져 같은 디스코드 · 구글 계정으로 새로 가입하면 정지가 없다(사용자 결정 「탈퇴는 된다」 그대로). 막으려면 정지된 사람이 탈퇴할 때 HMAC 만 따로 「차단 목록」 에 남기는 일이 필요하다(개인정보 안내 글도 같이 고쳐야 함 — 이번엔 안 함).
10. **운영 토큰 하나** — 운영자가 여럿이 되면 「누가」 가 모두 `ADMIN_NAME` 하나로 남는다. 그때는 토큰을 사람마다 따로 두는 손질이 필요하다.

## 11. 운영 — 다른 사용자 데이터 다루기(2026-10-18 사용자 결정 「명령으로」)

게임 화면에는 운영 도구가 없다. **운영자 토큰으로만 부르는 서버 주소**(`/api/admin/…`) + **이 PC 명령 `bz admin`**. 모든 쓰기 조치는 반드시 까닭(`reason`)이 있어야 하고, 조치와 같은 트랜잭션으로 **운영 기록**(`admin_log` — 누가 · 언제 · 무엇을 · 대상 · 까닭 · 바꾸기 전 값)에 남는다.

### 주소(운영자 전용 — `Authorization: Bearer <ADMIN_TOKEN>`)
| 주소 | 하는 일 |
|---|---|
| `GET /api/admin/user?id=` · `?nick=` · `?attempt=` · `?slot=`(하나만) | 찾기 · 보기 → `{ by, exact, users: [{ id, name, provider, created, nameChanged, lastActive, ban, hidden, sessions: { live, web, pc }, slots: { count, ok, pending, bad }, attempts, scores: { count, verified, pending, rejected }, best: [{ season, score }], recent(최근 시도 5 — 시도 id · 상태 · 점수), log(최근 운영 기록 5) }] }`. nick 은 겹침 열쇠가 같은 사람 먼저(`exact`), 그다음 부분 일치 10명. attempt = 랭킹 줄의 `attempt`. 읽기라 운영 기록에 남기지 않는다 |
| `GET /api/admin/log[?user=][&action=][&n=50]` | 운영 기록(최근 차례 · n 1~500) → `{ rows: [{ id, at, actor, action, user, name, target, reason, detail }] }` |
| `POST /api/admin/act { action, reason, dry?, … }` | 조치(아래 표). `dry: true` 면 바꾸지 않고 `plan` 만(운영 기록에도 안 남김) → 200 `{ ok, action, dry, plan, user(조치 뒤 요약), log(운영 기록 id) }` · 400(까닭 없음 · 인자) · 404(대상 없음) · 409(이미 그 상태 · 닉네임 겹침) |

|---|---|---|

| `unhide` | user · season?(없으면 그 사람의 숨김 전부) | 되돌리기 — 숨김이 없으면 409 |

### 명령 `bz admin`(`bolzena-core/Tools~/Dev/Admin.cs` — 콘텐츠를 읽지 않아 바로 뜬다)
```
bz admin user <대상>
bz admin rename <대상> <새 이름> --reason 까닭
bz admin clearname <대상> --reason 까닭
bz admin score delete <시도 id> --reason 까닭          (rejected 로: score reject <시도 id>)
bz admin hide <대상> [--season id] --reason 까닭      (season 이 없으면 모든 시즌)
bz admin unhide <대상> [--season id] --reason 까닭
bz admin slot delete <칸 id> --reason 까닭
bz admin slots purge <대상> --confirm --reason 까닭
bz admin ban <대상> (--days N | --forever) --reason 까닭
bz admin unban <대상> --reason 까닭
bz admin role <대상> tester|none --reason 까닭           (시험 계정 부여 · 회수 — 0009)
bz admin log [대상] [-n 50]
```
- **대상**: 숫자 · `id:12` = 사용자 번호 · 32자리 16진 · `attempt:…` = 시도 id(랭킹 줄 — 그 사람) · `slot:34` = 칸 id(그 주인) · `nick:1234`(숫자뿐인 닉네임) · 그 밖은 닉네임(겹침 열쇠가 같은 사람, 없으면 부분 일치가 하나일 때만 — 여럿이면 목록을 보여 주고 멈춘다).
- **쓰기 조치는 기본이 미리 보기** — 서버에 `dry` 로 물어 무엇을 할지(옛 값 → 새 값 · 지울 칸 수 · 풀리는 때)와 대상 요약만 보여 주고 끝. 실제로 하려면 같은 명령에 `--yes`. `--reason` 이 없으면 서버에 묻지도 않고 끝 코드 2.
- 주소 · 토큰: `--url` · `--token` 또는 환경 변수 `BZ_ADMIN_URL` · `BZ_ADMIN_TOKEN`(검증기 `BZ_VERIFY_*` 와 따로 — §7 7)). `--json` = 서버 응답 그대로.
- 끝 코드: 0 됨 · 1 서버가 거절(401 · 404 · 409 · 5xx) · 네트워크 · 2 쓰는 법 · 설정 · 400.
