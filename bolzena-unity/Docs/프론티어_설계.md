## 1. 결정성 — 다시 돌리면 같은 결과가 나오나

### 1.1 난수 원천은 하나뿐이다
- 엔진 난수는 `Runtime/Util/Rng.cs:9-41` 의 xorshift32(13 · 17 · 5) 하나. `double` 로 [0,1) 을 내고(`Rng.cs:26-32`), 정수는 `Math.Floor(Next()*n)`(`Rng.cs:35`). 반올림도 JS 식으로 직접 한다(`Rng.cs:46` `Num.Round`).
- 전투는 `Battle.Start` 에서 `new Rng(st.Seed)` 로 시작하고(`Runtime/Combat/Battle.cs:224-230`), 덱 섞기도 그 난수로(`Battle.cs:273`, `Battle.cs:445-449`).
- 판(Run)도 같은 난수기를 `RunState.RngState` 로 이어 쓴다(`Runtime/Run/Run.cs:20`, `Run.cs:77`, `Runtime/Run/RunState.cs:13`). 판이 여는 전투의 씨앗은 판 씨앗 · 층 · 칸 · 걸음으로 정해진다(`Run.cs:308`).
- 엔진(`Runtime/`) 안에 `System.Random` · `UnityEngine.Random` · `DateTime` 을 판 규칙에 쓰는 곳은 없다. `DateTime` 은 기록 시각뿐(`RunRecord.cs:63`, `Run.cs:863`).
- 유니티 쪽 `Random.Range` 는 전부 연출(타격 위치 · 목소리 · 몸짓 고르기 — `BattleDirector.Acts.cs:146,1779…`, `BattleDirector.Cards.cs:253`, `BattleDirector.Say.cs:94`). `CoreBattle.cs:74` 의 `System.Random` 은 `-battle` 시험 차림에서만 쓴다. 판 화면의 `RunPort.Rnd`(`bolzena-runui/Runtime/Data/RunPort.cs:20`)는 새 판의 마을 · 속성 굴림(`RunPort.cs:72,74`)뿐이고, 그 결과는 `NewRun` 인자로 들어가니 기록하면 된다.

### 1.3 지금 기록(RunRecord)으로 다시 돌릴 수 있나 — 못 한다
- 턴 녹화 `BattleTape.Card` 는 낸 카드 id(와 신탁 번호)만 적는다(`Runtime/Combat/BattleTape.cs:30-35`). **손패 몇 번째인지 · 대상 적 · 두 갈래 선택 · 소모량 · 버릴 카드 · 단계 · 고학년 대상**이 없다.
- 기록은 64KB 를 넘으면 턴 녹화부터 버린다(`RunRecord.cs:72`, `RunRecord.cs:143-165`).
- 판 쪽 선택(`PickLog`, `RunState.cs:113-120`)은 「무엇이 제시되고 무엇을 골랐나」 를 적지만 지도 이동 · 장비 끼기 · 상점 차례 · 이벤트 해소 같은 **판을 바꾸는 모든 호출**을 적지는 않는다.

### 1.4 다시 돌리는 데 더 필요한 것
**전투 하나**를 다시 돌리려면(프론티어에 충분):
1. `BattleSetup` 전부(`Battle.cs:7-43`) — 프론티어는 서버가 「사도 슬롯 + 보스 + 씨앗」 에서 똑같이 지을 수 있다.
2. 입력 테이프 — 전투를 바꾸는 호출은 넷뿐이다. 유니티 어댑터가 부르는 것도 이 넷이다(`CoreBattle.cs:385,388,532,543`):
   - `ApplyEpiphany(cardId, choice)`(`BattleCards.cs:246`)
   - `PlayCard(handIdx, targetIdx, PlayOpts{Choice, Spend, Discard, Stage, Ally, Spread})`(`BattleCards.cs:304`, `Battle.cs:58-73`)
   - `UseUlt(heroKey, targetIdx, stage)`(`BattleCards.cs:176`)
   - `EndTurn()`(`BattleTurn.cs:183`)
3. 같은 콘텐츠(콘텐츠 스냅샷 해시) · 같은 엔진(버전 + 규칙 지문).
4. 어긋남을 찾을 「턴 지문」 — 턴 끝마다 `Rng.State` · 파티 HP · 적 HP · 손패 · 더미 수를 해시. 클라이언트와 서버가 몇 턴째에서 갈렸는지 바로 보인다.

**판 전체**를 다시 돌리려면(사도 슬롯 검증용 — 뒤 단계): 판을 바꾸는 호출 전부를 적어야 한다. 다행히 판 화면은 「판을 바꿀 때 이 문만 지난다」 는 어댑터가 있다(`bolzena-runui/Runtime/Data/RunPort.cs:10-13`) — `NewRun`(`:84`) · `Enter`(`:101`) · `OpenFight/Finish`(`:154-167`) · `TakeGold/TakeEquip/ClaimGlow/BossCopy/Advance`(`:182-187`) · 야영(`:191-194`) · 상점(`:199-213`) · 이벤트(`:222-234`) · `AssignNeutral`(`:249`) 등 약 25개. 다만 화면(Flow 폴더)이 `Run.TakeFlash` · `TakeGrade` · `GradeRemove` · `CampOffer` · `AssignNeutral` 을 어댑터를 건너 직접 부르는 곳이 있어 먼저 어댑터로 모아야 한다.

## 2. 사도 상태 — 판이 끝날 때 사도 한 명에게 남는 것

### 2.1 덱은 공용 목록이지만 카드마다 주인이 있다
- 판 상태의 덱은 판 전체에 한 줄 `List<string> Deck`(`RunState.cs:24`). 시작 덱은 사도마다 시작 카드를 이어 붙인 것(`GameData.cs:316`).
- 그러나 **카드마다 주인이 정해진다**:
  - 사도 카드 — `CardDef.Hero`(`Runtime/Data/Defs.cs:285-287`).
  - 교주 카드 — 덱의 id 가 `카드@사도`(`GameData.cs:189-205`). 얻으면 사도를 고르게 하고(`RunState.cs:75-79` `NeutralWait`, `Run.cs:47-64`) 그 사도 몫으로 낸다.
  - 같은 카드 여러 장은 `#n` 으로 한 장씩 갈린다(`GameData.cs:206-240`) — 신탁 · 축복이 한 장에만 붙는다.
  - **예외: 상태 · 저주 카드는 주인이 없다**(`Defs.cs:339-342` — 「상태 · 저주는 주인 없이 덱의 묶음으로」).
- 그러니 「사도 A 의 덱」 = `Deck` 에서 주인이 A 인 카드. 사도별 저장은 구조상 말이 된다.

### 2.2 사도 한 명에게 묶이는 것 · 안 묶이는 것

### 2.3 저장 슬롯 형식(제안)
```json
{
  "kind": "bolzena-hero-slot", "v": 1,
  "hero": "sion",
  "engine": "core a1d1c22", "content": "sha256:…(CoreData 스냅샷)", "rules": "sha256:…(R 손잡이)",
  "from": { "seed": 123456, "result": "win", "floor": 2, "ended": "2026-10-18T12:34Z" },
  "cards": [
    { "id": "sion_shot",    "o": 3, "b": "own1", "vals": { "충전": 2 } },
    { "id": "sion_shot#2" },
    { "id": "n_guard@sion", "o": 1 }
  ],
  "gear": { "무기": "eq_rifle", "장신구": "eq_ring" },
  "growth": { "atk": 2, "def": 0, "crit": 1 }
}
```
- 숫자 능력치는 **적지 않는다** — 데이터 + 장비 + 성장에서 다시 셈(위조 여지가 줄고 데이터 수치 조정을 그대로 따라감).
- 카드 id 는 덱에 있던 그대로(한 장 번호 · 주인 꼬리 포함) — `Flash/Shin/CardVals` 키와 같아야 한다.
- 직렬화 지점: **판이 끝나는 순간, `RunRecord.Of` 를 부르는 같은 자리**(`RunRecord.cs:98` — 모든 `AfterFight` 가 끝난 뒤). 엔진에 `HeroSlot.Of(Run run, string heroKey)` 순수 함수를 둔다(봇 판에도 그대로).
- 프론티어 전투를 열 때는 슬롯 셋을 `BattleSetup` 으로 합친다: `Party` = 슬롯 사도들, `Deck` = 카드 합, `Flash/Shin/CardVals` = 합친 표, `Gear/GearRules` = 장비 id 로 `Run.StatsOf/GearRules` 와 같은 셈, `Growth` = 슬롯 성장, `PartyHp` = 비움(가득), `Glow` = 없음(결정 필요).
- 섞을 때 조심: 엔진은 사도를 열쇠(`Unit.Key`)로 찾는다(`Battle.cs:436-441` `HeroUnit`, `BattleTally.cs:27-31`, `BattleSetup.Gear` 사도 키). **같은 사도 둘은 한 파티에 못 넣는다**(다른 판의 같은 사도 슬롯 둘도 안 됨).

## 3. 서버 재계산 방법

엔진은 이미 유니티 없이 돈다 — `Tools~/Dev/Dev.csproj` 가 `../../Runtime/**/*.cs` 를 net8.0 콘솔로 빌드하고 Newtonsoft.Json 하나만 쓴다(`bz` 명령). 이것이 모든 선택지의 출발점이다.

| **(a) .NET → WASM, Workers 에서 바로** | `dotnet` wasm(브라우저 또는 WASI 실험 대상)으로 엔진 + 콘텐츠를 묶어 Pages Function 이 부른다 | 중간(빌드 맞추기 · JS 접착) | **크다.** Workers 스크립트 크기 한도(무료 3MB · 유료 10MB 압축 — 지금 값 확인 필요) 안에 .NET 런타임 + 엔진 + Newtonsoft + 콘텐츠(`StreamingAssets/CoreData` 1.6MB)를 넣어야 함. 인터프리터라 느리고, 1.6MB JSON 파싱만으로 무료 CPU 한도(요청당 10ms)를 넘는다 → 유료 플랜 필수. | (d-2) 클라이언트 서명 · 상호 확인 | — | — | 클라이언트를 고치면 무력 | 안 씀. |

**(c) 검증기를 어디서 돌리나**
- 사용자 PC 예약 작업: 돈 0, 바로 됨. PC 가 꺼지면 멈춤. PC 자원 한도(CPU 70% · 동시 작업 2개)와 겹치지 않게 한 번에 하나씩.
- GitHub Actions 예약(cron 최소 5분 간격, 실제론 더 늦을 수 있음): 공개 저장소면 사실상 무료, 비공개면 월 무료 분수 안. 콘텐츠 스냅샷 · 엔진이 저장소에 있어야 함(원작 자료가 들어 있으니 비공개 저장소로).
- 작은 VPS: 늘 켜짐. 월 몇 달러 + 관리.
- 추천 순서: **PC 예약 작업으로 시작 → 사람이 늘면 Actions 또는 Containers.** 검증기는 「대기 줄 가져오기 · 결과 쓰기」 HTTP 두 개만 알게 해 어디로든 옮길 수 있게 한다.

**검증 흐름**
1. 시작 — 게임이 `/api/frontier/start` 에 슬롯 id 셋을 보내면 서버가 **씨앗을 내준다**(시도 id 와 함께 D1 에 적음). 씨앗을 클라이언트가 고르면 좋은 패가 나올 때까지 다시 굴릴 수 있다.
2. 전투 — 클라이언트는 평소처럼 엔진을 돌리며 입력 테이프와 턴 지문을 적는다. 점수는 바로 보인다.
3. 끝 — `/api/frontier/submit` 에 {시도 id · 테이프 · 주장 점수 · 턴 지문}. 서버는 모양 · 크기 검사 후 「검증 대기」 로 넣는다. 랭킹판엔 「검증 중」 으로 보인다.
4. 검증기 — 서버에 있는 슬롯 셋 + 씨앗 + 테이프로 다시 돌려 점수 · 지문이 같으면 승인, 다르면 거절 + 어긋난 턴.

## 4. 계정

### 4.1 OAuth(Pages Functions)
- 주소: `/api/auth/discord/start` · `/api/auth/discord/callback` · `/api/auth/google/start` · `/api/auth/google/callback` · `/api/auth/me` · `/api/auth/logout`.
- 흐름: start 가 `state`(+ 구글은 PKCE)를 짧은 쿠키에 두고 공급자로 보냄 → callback 이 `state` 를 맞춰 보고 코드를 토큰으로 바꿈(비밀 키는 Pages 환경 변수) → 공급자의 사용자 번호만 받아 D1 `users` 에 넣거나 찾음 → **세션 토큰(무작위 32바이트)** 을 만들어 해시만 D1 `sessions` 에 두고 쿠키 `HttpOnly; Secure; SameSite=Lax` 로 줌.
- **JWT 보다 무작위 토큰 + D1** 을 추천: 로그아웃 · 계정 삭제 때 바로 끊을 수 있고, 어차피 요청마다 D1 을 읽는다(서명 키 관리도 없음).
- 받는 범위 최소: 디스코드 `identify` 만(이메일 안 받음), 구글 `openid` 만. 화면 이름은 사용자가 따로 정하게(디스코드 닉네임 · 구글 이름을 랭킹에 그대로 안 띄움).
- 남용 막기: 지금 `record.js` 처럼 다른 사이트 요청 거절(`bolzena-unity/Web/functions/api/record.js` 의 origin 검사) · 분당 횟수.

### 4.2 유니티에서 로그인
- **WebGL**: 게임과 API 가 같은 도메인(bolzena.pages.dev)이라 브라우저가 쿠키를 알아서 붙인다. 지금 기록 보내기도 같은 도메인 주소를 쓴다(`bolzena-runui/Runtime/Kit/PlayRecord.cs:197`). 로그인 버튼은 같은 탭에서 `/api/auth/discord/start?back=/` 로 갔다가 돌아옴(게임이 다시 로드되니 판 저장이 먼저 되어 있어야 함 — 이미 있음).
- **PC**: 「기기 코드」 방식. 게임이 `/api/auth/pc/start` 로 짧은 코드(예: `K7Q-2M9`)와 주소를 받아 브라우저를 연다 → 사용자가 웹에서 로그인 후 코드 확인 → 게임은 `/api/auth/pc/poll` 을 몇 초마다 물어 긴 토큰(Bearer)을 받아 기기에 저장. 딥링크(사용자 정의 주소) 등록이나 로컬 포트 열기보다 단순하고 방화벽 문제가 없다.

### 4.3 KV 냐 D1 이냐
- **D1**: 랭킹은 「이번 시즌 · 이 보스 · 점수 내림차순 · 검증된 것만 · 사람당 최고 하나」 같은 질의가 핵심이라 SQL 색인이 맞다. 사용자 · 세션 · 슬롯 · 시도도 서로 엮인다. 무료 한도로 초기엔 충분(값은 확인 필요).
- **KV**: 지금 익명 판 기록(`record.js`, 키 `v2/날짜/익명id/씨앗/결과`)에 그대로 둔다. 랭킹 질의엔 안 맞음(키 목록 훑기뿐, 무료 쓰기 하루 1000번 — `record.js` 머리 주석).
- 테이프가 커지면 R2 에 두고 D1 엔 열쇠만. 처음엔 D1 TEXT 로 충분(입력 테이프는 턴당 수십 바이트).

## 6. 위험 · 열린 문제

1. **저장 사도 위조(가장 큼).** 프론티어 전투를 다시 돌려도, 슬롯 덱이 「판에서 정말 얻은 것」 인지는 모른다. 규칙 검사로는 「합법한 최강 덱」 위조를 못 막는다. 확실히 막으려면 판 전체 입력 기록을 다시 돌려야 한다(1.4 — `RunPort` 를 거치는 약 25개 호출 + 화면이 직접 부르는 5개, 판 이어하기 때 기록도 이어지게). 7단계로 둔다.
2. **데이터가 바뀌면 옛 슬롯은?** 카드 수치 · 신탁이 바뀌면 같은 슬롯이 다른 덱이 된다. 시즌마다 엔진 · 콘텐츠를 고정하고, 슬롯엔 만든 때의 콘텐츠 해시를 남긴다. 선택지: (가) 시즌이 바뀌면 옛 슬롯도 새 데이터로 해석(없어진 카드 · 신탁 번호는 빼거나 바꿈 — 바꿈 표 필요), (나) 옛 슬롯은 「옛 시즌용」 으로 잠금, (다) 큰 개편 때 슬롯 초기화. 검증기는 **그 시즌의 엔진 · 콘텐츠 스냅샷**으로 돌려야 하니 스냅샷을 해시별로 보관한다. 지금 빌드가 콘텐츠 검사 오류 하나 때문에 옛 스냅샷을 쓰는 중이라, 「어느 스냅샷으로 검증하나」 를 처음부터 기록에 박아야 한다.
3. **유니티 ↔ .NET 8 차이.** 컬렉션 구현 · 컴파일러 차이로 어긋날 수 있다(1.2). 배포 전 시험: 같은 테이프를 에디터 · WebGL 빌드 · PC 빌드 · `bz` 에서 돌려 지문이 같은지.
4. **밸런스.** 긴 보스 단일전에서 쌓이는 엔진(겹 · 성장 · 「매 턴 +」)이 폭주할 수 있다(레이드 계획 메모: 아야 「만년설의 앎」 덤 상한). 시즌 보스마다 봇으로 점수 분포를 먼저 잰다.
5. **씨앗 고르기 · 무한 재시도.** 서버가 씨앗을 주고 시도 횟수를 제한(하루 N번 · 시작한 시도는 포기도 기록). (2026-10-19 — 하루 한도는 없애고 재시도를 노력으로 인정하기로 함 · 결정 7) 시즌 공용 씨앗이면 공정하지만 오프라인으로 최적 수를 찾기 쉽다.
6. ~~**교주 보드(크레파스).**~~ 2026-10-21 보드를 없애 해당 없음.
7. **주인 없는 상태 · 저주 카드.** 저장 때 버리면 「저주를 모은 채 저장하면 사라짐」 이 되어 판 전략이 바뀐다 — 편성 사도들에 나눠 담을지, 버릴지 정해야 함.
8. **개인정보.** 계정이 생기면 「누구인지 알 수 있는 정보」 를 처음 받는다(지금 기록은 익명 — `RunRecord.cs:12`, `record.js` 머리 주석). 받는 범위 최소화, 개인정보 처리 안내 글, 계정 · 슬롯 삭제 버튼, 탈퇴 시 랭킹에서 지움. 기존 익명 기록과 계정을 잇지 않는다.
9. **원작 IP 와 공개 서비스.** 트릭컬 사도 · 카제나 체계를 쓰는 비공식 팬 게임에 계정 · 랭킹을 붙이면 「서비스 운영」 으로 보일 여지가 커진다. 수익 없음 · 비공식 표기 · 권리자 요청 시 내림을 분명히 하고, 원작사 2차 창작 가이드라인을 다시 확인할 것.
10. **비용.** D1 · Pages 무료 한도로 시작 가능. (a) WASM 이나 Containers 를 쓰면 Workers 유료 플랜. 검증기를 PC 에서 돌리면 0원이지만 PC 가 꺼지면 검증이 멈춤.

## 7. 만드는 순서

각 단계는 앞 단계에만 기대고, 끝에 확인 방법이 있다.

### 1단계 — 입력 테이프와 다시 돌리기(엔진만)
- `Runtime/Combat/BattleInput.cs`: 네 호출을 적는 테이프 + `Replay(GameData, BattleSetup, tape)` + `Battle.Digest()`(턴 끝마다 `Rng.State` · 파티 HP · 적 HP · 손패 · 더미 수 해시).
- `R` 손잡이 지문 함수 · 콘텐츠 폴더 해시 함수. `bz replay <파일>`.
